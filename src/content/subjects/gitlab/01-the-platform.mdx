Most teams assemble a toolchain: a Git host, a CI service, an artifact registry,
a vulnerability scanner, a deployment tool, an issue tracker. Each has its own
permissions, its own webhooks, and its own idea of what "the pipeline" means.
GitLab's pitch is that all of those are **one application over one data model**,
so a commit, the merge request that carries it, the pipeline that built it, the
scan that flagged it and the environment it landed in are all rows that already
know about each other.

That's the feature you're actually buying. Every individual capability below has
a stronger standalone competitor; what none of them have is the join.

## Editions and tiers

There is one codebase, shipped two ways.

- **GitLab CE** — the open-source Community Edition (MIT).
- **GitLab EE** — the same code plus proprietary features, gated at runtime by
  a licence key. The tiers are **Free**, **Premium** and **Ultimate**.

Roughly where the line falls, because it determines which features you can even
plan around:

| Tier | Representative features |
| --- | --- |
| Free | Repos, issues, merge requests, full CI/CD, container and package registries, basic secret detection |
| Premium | Merge request approval rules, merge trains, protected environments, code owners, multiple issue boards, epics |
| Ultimate | The full security scanner suite (SAST, DAST, dependency, licence, fuzz), security and vulnerability dashboards, compliance frameworks, portfolio management |

The pattern is worth internalising: **the CI/CD engine itself is free**, at any
scale you can supply runners for. What the paid tiers sell is *governance around*
CI/CD — who may approve, what must pass, which environments are protected, and
the dashboards that aggregate the results.

## Where it runs

- **GitLab.com** — the multi-tenant SaaS instance. Shared runners are metered in
  **compute minutes**; you can always attach your own runners instead and pay
  nothing for compute.
- **GitLab Self-Managed** — you run the instance (Omnibus package, Docker, or the
  Helm chart on Kubernetes). Your data, your upgrade schedule, your runners.
- **GitLab Dedicated** — single-tenant SaaS, hosted by GitLab in a region you
  pick. The compliance answer for people who cannot use the shared instance but
  don't want to operate one.

## Groups, projects, namespaces

Everything is namespaced under a **group**, groups nest arbitrarily, and a
**project** is the leaf that holds a repository, its issues, its pipelines and
its registries.

This is not just tidiness. Nearly every setting cascades down the group tree:
members and their roles, CI/CD variables, runners, compliance frameworks, push
rules, approval policies. A CI/CD variable defined on the top-level group is
visible to every pipeline in every project beneath it, which is why "where do I
put this secret?" is usually answered with "as high in the tree as it is allowed
to be needed, and no higher."
