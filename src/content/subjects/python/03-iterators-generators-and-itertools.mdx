A `for` loop doesn't know anything special about lists, dicts, or files — it
only knows one protocol, and every iterable implements it.

```python
it = iter(obj)          # __iter__() -- get an iterator
while True:
    try:
        item = next(it)  # __next__() -- get the next value
    except StopIteration:
        break
    ...                  # loop body
```

Anything with `__iter__` and `__next__` can stand in for `obj`. Writing that
by hand is mostly boilerplate:

```python
class Countdown:
    def __init__(self, start):
        self.n = start

    def __iter__(self):
        return self

    def __next__(self):
        if self.n <= 0:
            raise StopIteration
        self.n -= 1
        return self.n + 1
```

## `yield` writes the class for you

A **generator function** — any function containing `yield` — compiles to an
object that implements this same protocol automatically. Calling it doesn't
run the body; it returns a paused generator that runs up to the next `yield`
each time `next()` is called on it.

```python
def countdown(start):
    n = start
    while n > 0:
        yield n
        n -= 1
```

Same behavior as `Countdown` above, in four lines instead of a class. The
function's local state — `n`, and its position in the loop — is preserved
across suspensions, which is the part that would otherwise need to become
instance attributes by hand.

## Why this changes memory behavior

A generator produces values **one at a time, on demand** — it never
materializes a full collection. Swap a list comprehension for a generator
expression and the difference isn't style, it's whether the whole result
exists in memory at once:

```python
squares = [x * x for x in range(10_000_000)]     # builds a 10M-int list, all at once
total = sum(x * x for x in range(10_000_000))     # one int in flight at a time
```

The second line holds one value at a time no matter how large the range is —
`sum()` pulls, squares, adds, and discards, on repeat. This is also why
chaining generator expressions (`sum(x for x in (y*y for y in data))`)
composes for free: nothing downstream forces anything upstream to finish
first.

One sharp edge worth knowing: since Python 3.7 ([PEP
479](https://peps.python.org/pep-0479/)), a `StopIteration` raised *inside* a
generator's body no longer silently ends the generator — it's converted into
a `RuntimeError`. Before that change, an accidental `StopIteration` deep in
a call stack could make a generator stop early with no error at all, which
was a genuinely hard bug to track down.

## The itertools toolbox

`itertools` is the standard library's set of lazy, composable building
blocks — all of them return iterators, none of them build an intermediate
list.

| Function | Does |
| --- | --- |
| `chain(*iterables)` | Walks multiple iterables as if they were one, lazily. |
| `islice(it, stop)` | Slices an iterator (`it[:stop]` doesn't work — iterators aren't subscriptable). |
| `groupby(it, key)` | Groups **consecutive** items sharing a key — needs input pre-sorted by that key. |
| `tee(it, n)` | Splits one iterator into `n` independent ones — each unconsumed branch buffers in memory. |
| `product`, `combinations`, `permutations` | Lazy Cartesian product and combinatorics, without nested loops. |

The `groupby` caveat trips people up constantly: it groups adjacent
duplicates, not all duplicates. `groupby(sorted(data, key=k), key=k)` is
correct; `groupby(data, key=k)` on unsorted `data` silently produces one
group per unsorted run, not one group per key.
