Assignment inside a function makes a name **local** to that function by
default — even if a same-named variable exists at an outer scope, even if
the assignment happens after a read that looks like it should hit the outer
one. That mismatch is what `global` and `nonlocal` exist to override:

```python
count = 0

def outer():
    total = 0
    def inc():
        nonlocal total   # without this, `total += 1` below is UnboundLocalError
        total += 1
        return total
    return inc
```

`nonlocal` reaches into the nearest **enclosing function** scope.  `global`
reaches straight to module scope, skipping any enclosing functions in
between. Neither exists for reading — only assignment needs them, because
reads already fall through the LEGB chain on their own.

## The closure trap: loop variables are not snapshotted

This is the single most common closure bug, and it survives even in
experienced hands because the code reads as if it should obviously work:

```python
funcs = [lambda: i for i in range(3)]
[f() for f in funcs]        # [2, 2, 2] -- not [0, 1, 2]
```

A closure captures the **variable**, not the value it held at creation time.
All three lambdas share the same `i`, and by the time any of them runs, the
loop has finished and `i` is `2`. This is *not* unique to lambdas — a `def`
created in a loop body has the exact same problem.

Two fixes, both forcing the value to be captured at creation time instead of
at call time:

```python
# 1. Default argument — evaluated once, at function-definition time
funcs = [lambda i=i: i for i in range(3)]

# 2. A factory function — gives each closure its own local `i`
def make(i):
    return lambda: i

funcs = [make(i) for i in range(3)]
```

## What `@decorator` actually does

A decorator is just a function that takes a function and returns a
(usually different) function. `@decorator` above a `def` is sugar for
reassigning the name after defining it:

```python
@decorator
def f():
    ...

# is exactly:
def f():
    ...
f = decorator(f)
```

A decorator **taking arguments** needs one more layer — the outer call
produces the actual decorator, which then wraps the function:

```python
import functools

def retry(times):
    def decorator(fn):
        @functools.wraps(fn)
        def wrapper(*args, **kwargs):
            for attempt in range(times):
                try:
                    return fn(*args, **kwargs)
                except Exception:
                    if attempt == times - 1:
                        raise
        return wrapper
    return decorator

@retry(3)
def flaky():
    ...
```

`@retry(3)` calls `retry(3)` immediately, which returns `decorator` — *that*
is what actually wraps `flaky`. Skip `functools.wraps` and `wrapper` silently
replaces `flaky`'s `__name__`, `__doc__`, and signature everywhere —
tracebacks, `help()`, and introspection-based tools (like most web
frameworks' routers) all see `wrapper` instead of the function you wrote.

Stacking decorators applies bottom-up but executes outside-in:

```python
@a
@b
def f(): ...

# equivalent to: f = a(b(f))
# so at call time: a's wrapper runs first, then calls into b's wrapper, then f
```
