CPython's **Global Interpreter Lock (GIL)** allows only one thread to execute
Python bytecode at any given instant, no matter how many CPU cores the
machine has. It exists because CPython's memory management — reference
counting on every object, on every assignment — isn't thread-safe by itself;
the GIL is the one big lock that makes it safe without needing a lock around
every object.

That sounds like threads are pointless in Python — they're not, because the
GIL is **released** around blocking I/O (network calls, disk reads, `time.sleep`)
and around long native calls in C extensions (numpy, most compiled
libraries). A thread doing nothing but waiting on a socket isn't holding the
GIL, so other threads run freely during that wait.

## Picking a model

| Model | Good for | Why |
| --- | --- | --- |
| `threading` | I/O-bound work: network calls, disk, subprocess waits | The GIL releases during blocking I/O, so waiting threads overlap instead of serializing. |
| `multiprocessing` | CPU-bound work: parsing, number-crunching, image processing | Each process gets its own interpreter and its own GIL — this is the only way pure-Python code uses more than one core at once. |
| `asyncio` | Very high volumes of concurrent I/O (thousands of open connections) | Single thread, cooperative scheduling at every `await` — no GIL contention, no per-thread OS overhead, but every library on the path has to be async-aware. |

The costs run the opposite direction: `multiprocessing` gets real
parallelism but pays for it in process startup time and in serializing
(`pickle`) every argument and return value across the process boundary —
sharing memory between processes is the exception, not the default.
`asyncio` avoids that cost entirely but only works with libraries that speak
`async`/`await`; a single blocking call anywhere in an async codebase stalls
every other coroutine sharing that thread.

A CPU-bound function inside a library that releases the GIL for its native
computation (numpy's array math, for instance) is the one case where
`threading` *does* speed up CPU-bound work — the parallelism is happening in
C, outside the GIL's reach, while Python's own bytecode loop stays
single-threaded.

One more moving target worth knowing about: [PEP
703](https://peps.python.org/pep-0703/) introduced an optional
**free-threaded** CPython build (available as of 3.13) that can run without
the GIL at all. It's opt-in and still maturing — most third-party C
extensions haven't caught up yet — but it's the first real crack in an
assumption that's held since CPython 1.x.
