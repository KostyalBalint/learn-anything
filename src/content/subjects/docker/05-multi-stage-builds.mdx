A naive Dockerfile for a compiled or bundled app tends to ship its entire
build toolchain — compiler, package manager cache, dev dependencies — inside
the image that runs in production. None of that is needed at runtime; it's
dead weight that makes images slower to pull and widens what's exposed if the
container is ever compromised.

**Multi-stage builds** solve this with more than one `FROM` in a single
Dockerfile. Each `FROM` starts a new, independent stage; a later stage can
`COPY --from=<stage>` specific files out of an earlier one, and only the
*final* stage becomes the image that gets tagged.

```dockerfile
# ---- build stage ----
FROM node:20 AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build          # produces /app/dist

# ---- runtime stage ----
FROM node:20-slim
WORKDIR /app
COPY --from=build /app/dist ./dist
COPY package.json package-lock.json ./
RUN npm ci --omit=dev
CMD ["node", "dist/server.js"]
```

The `node:20` build stage — full toolchain, dev dependencies, source maps,
everything `npm run build` needed — never gets tagged or pushed. Only `dist/`
and production dependencies cross into the `node:20-slim` runtime stage that
actually ships.

Figures above are illustrative, but the shape holds for any compiled or
bundled language: Go binaries dropped into `scratch` or `distroless`, a Java
`.jar` copied out of a Maven build stage into a JRE-only image, a Vite/webpack
`dist/` copied into `nginx:alpine`. Same pattern every time — build fat,
ship thin.

## Naming and targeting stages

`AS build` names a stage so later stages (or the CLI) can reference it. You
can also stop the build early at a specific stage — useful for a dev image
that *should* keep the toolchain:

```bash
docker build --target build -t myapp:dev .     # stop at the build stage
docker build -t myapp:1.4 .                    # default: build through the last stage
```

That's one Dockerfile serving both a full-toolchain dev image and a minimal
production image, with the shared early layers (base image, dependency
install) cached and reused between the two.
