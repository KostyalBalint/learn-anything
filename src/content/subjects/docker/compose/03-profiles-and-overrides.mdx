A single `compose.yaml` checked into the repo is meant to be shared by
everyone — but "everyone" still needs different secrets, and dev usually
wants tools prod doesn't. Compose has three separate mechanisms for that, and
they solve different problems.

## `.env` files: values, not structure

A `.env` file next to `compose.yaml` is loaded automatically and its values
substitute into `${VAR}` references in the file — it changes *values*, never
the file's shape:

```bash
# .env (gitignored — real secrets, per machine)
POSTGRES_PASSWORD=hunter2
```

```yaml
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
```

`.env` belongs in `.gitignore`; commit a `.env.example` with the keys but
dummy values instead, so the file's *shape* is documented without leaking
anyone's real secrets. A service's `env_file:` key does something related but
distinct — it loads a whole file's worth of variables *into that container's
environment*, rather than substituting into the YAML.

## Profiles: services that only run on request

`--profile` marks a service as opt-in instead of always started by `up`:

```yaml
services:
  web:
    build: .
    # no profile: always starts with plain `docker compose up`

  pgadmin:
    image: dpage/pgadmin4
    profiles: ["debug"]
```

```bash
docker compose up -d                    # web only
docker compose --profile debug up -d    # web + pgadmin
```

This is how one file serves both "just run the app" and "run the app plus
the admin UI I only want open occasionally" — without maintaining a second,
mostly-duplicate compose file for the debug tooling.

## Override files: layering, not duplicating

Compose merges multiple `-f` files in order, later files overriding or
extending earlier ones field-by-field — not replacing the whole service.
`docker compose up` alone already auto-loads `compose.yaml` +
`compose.override.yaml` if the latter exists, which is exactly the dev-only
layer:

```yaml
# compose.override.yaml (dev — loaded automatically, usually gitignored)
services:
  web:
    volumes:
      - .:/app          # bind-mount source for live reload
    environment:
      LOG_LEVEL: debug
```

```yaml
# compose.prod.yaml (explicit opt-in)
services:
  web:
    restart: always
```

```bash
docker compose up -d                                       # base + override (dev)
docker compose -f compose.yaml -f compose.prod.yaml up -d   # base + prod, override skipped
```

The base file stays the single source of truth for what the app *is*
(services, images, how they connect); override files only adjust *how* it
runs in a given environment. That split is what keeps a team's `compose.yaml`
usable by everyone — no `if dev then` branches inside it, no prod-only
service definitions someone has to remember to strip out locally.
