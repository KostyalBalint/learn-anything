Kubernetes has no `User` object. Human identity is somebody else's problem —
certificates, OIDC, a cloud IAM integration. What it *does* model is the identity
of **in-cluster workloads**: the ServiceAccount.

Every Pod runs as one. Omit `serviceAccountName` and you get the namespace's
`default` ServiceAccount, which exists in every namespace and is created for you.
So the question is never "does this Pod have an identity", only "which one, and
what is it allowed to do".

The token authenticates the Pod to the API server as the username
`system:serviceaccount:<namespace>:<name>`. That string is what a RoleBinding
names as its subject — ServiceAccounts have no permissions of their own, they're
just the thing bindings point at.

## Tokens changed, and the old mental model is wrong

Old clusters (pre-1.24) created a **Secret** per ServiceAccount holding a
never-expiring JWT, valid for any audience, forever, for anyone who obtained it.
Copy it out of the cluster and it kept working.

Modern clusters use **projected, bound tokens**: the kubelet asks the API server
for a token scoped to a specific audience, with an expiry (an hour by default),
bound to *that specific Pod object*. The kubelet refreshes it in place, and when
the Pod is deleted, the token is invalid even if it hasn't expired. Stolen tokens
now have a short, tightly-scoped life.

Consequences that catch people out:

- The client must **reread the file**. A library that loaded the token once at startup gets 401s an hour later. The official client libraries handle it; hand-rolled `curl` scripts do not.
- `kubectl create token <sa>` is how you mint one by hand now, with a `--duration` you choose. Creating a ServiceAccount no longer creates a Secret.
- The legacy no-expiry Secret can still be forced (`type: kubernetes.io/service-account-token`). Don't. It's the exact thing bound tokens exist to eliminate.

## Turning it off

Every Pod gets the token mounted at
`/var/run/secrets/kubernetes.io/serviceaccount/token` by default — including the
overwhelming majority that never call the API server. That's a free credential
sitting in the filesystem of every compromised container.

```yaml
spec:
  automountServiceAccountToken: false
```

Set it on the Pod, or on the ServiceAccount to cover everything using it. If your
app doesn't talk to the API server, it should have no token to steal. Do this to
`default` in each namespace and you've removed a whole class of pivot.

The other half: **give each workload its own ServiceAccount**. The shared
`default` accumulates whatever anyone bound to it, and every Pod in the namespace
inherits the maximum. One SA per Deployment, bound to exactly what it needs.

## Reaching outside the cluster

The same projection mechanism does cloud identity. The API server can issue a
token with an audience like `sts.amazonaws.com`, and the cloud provider is
configured to trust the cluster's OIDC issuer — so AWS IRSA, GKE Workload
Identity and Azure Workload Identity all work by exchanging a projected
ServiceAccount token for cloud credentials. No static cloud keys in a Secret,
no key rotation, and the same short expiry.
