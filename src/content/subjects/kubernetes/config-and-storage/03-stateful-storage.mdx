A Deployment's Pods are interchangeable, so a volume attached to "the
Deployment" makes no sense — every replica would want the same disk. A
**StatefulSet** exists for the opposite case: replica `db-0` is not replica
`db-1`, and each one owns its data.

Three guarantees follow from that, and they're a package deal:

- **Stable name.** `db-0`, `db-1`, `db-2` — ordinal, not a random suffix.
- **Stable network identity.** `db-0.db.prod.svc.cluster.local`, via the headless Service.
- **Stable storage.** Its own PVC, reattached to whatever node the Pod lands on.

## volumeClaimTemplates, not volumes

A Deployment names an existing PVC — everyone shares it. A StatefulSet declares a
**template**, and the controller creates one PVC per replica, named
`<template>-<statefulset>-<ordinal>`. That naming *is* the mechanism: when `db-1`
is deleted and recreated on another node, the controller looks for `data-db-1`,
finds it already exists, and reattaches it. Same disk, same data, new Pod.

Scale to 5 and you get `data-db-3` and `data-db-4`, provisioned fresh.

## Deleting a StatefulSet keeps the disks

Scale down to 3 and the PVCs for `db-3`/`db-4` are **not** deleted. Delete the
StatefulSet entirely and the PVCs still stay. This is on purpose: the controller
assumes the data matters more than the tidiness, and scaling back up must
reattach the original volumes.

The consequence is that a scale-down is not a cleanup, and the disks keep costing
money until someone deletes the PVCs by hand. Newer clusters have
`persistentVolumeClaimRetentionPolicy` to opt into deletion on scale-down or
delete — an opt-in, never the default.

## Ordering, and how to turn it off

By default (`podManagementPolicy: OrderedReady`) the controller starts `db-0`,
waits for it to be Ready, then starts `db-1`. Scale-down runs in reverse:
highest ordinal first. That's what a primary/replica database wants, and it's
also why a StatefulSet whose `db-0` is crashlooping will never start `db-1` — the
rollout is stuck behind a Pod that never goes Ready.

Set `podManagementPolicy: Parallel` when the replicas are peers with no boot
ordering (a sharded cache, say). You keep the identity and the per-replica
storage, and lose only the sequencing.
