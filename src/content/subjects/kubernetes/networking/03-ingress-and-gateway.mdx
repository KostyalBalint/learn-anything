A `LoadBalancer` Service gets you one cloud load balancer, one IP and one bill,
per Service. Twenty microservices means twenty of each. **Ingress** collapses
that: one load balancer at the edge, routing by host and path to ClusterIP
Services behind it.

## The Ingress object does nothing

This trips people up: creating an Ingress in a cluster with no **Ingress
controller** installed is a no-op. The object is inert routing configuration. A
controller — nginx, Traefik, HAProxy, a cloud one — watches Ingress objects and
programs an actual proxy. No controller, no traffic, no error. Just an Ingress
with no address, forever.

`ingressClassName` picks *which* controller adopts the object, for clusters
running more than one (an internal and an external one, typically).

## Where Ingress runs out

The spec covers HTTP host/path routing and TLS termination. It does not cover
header matching, traffic splitting, retries, gRPC, or anything else — so every
controller grew its own annotations:

```yaml
nginx.ingress.kubernetes.io/rewrite-target: /$2
nginx.ingress.kubernetes.io/canary-weight: "20"
```

Which are, by definition, not portable. "Standard Ingress plus forty vendor
annotations" is the normal state of a production cluster, and swapping
controllers means rewriting all of them.

## Gateway API: the same traffic, different owners

The **Gateway API** is the successor, and its central move is splitting one
object into three, along the lines of who actually owns what:

| Resource | Owned by | Says |
| --- | --- | --- |
| `GatewayClass` | The cluster provider | What kind of infrastructure exists (this is Envoy, this is a cloud LB). |
| `Gateway` | The platform team | An actual listener: ports, protocol, TLS certs, which Routes may attach. |
| `HTTPRoute` | The app team | Match on host, path, header, method; split by weight; rewrite; point at Services. |

That's the real motivation. With Ingress, changing a path meant editing an object
that also held the TLS config and the LB annotations — so either the app team got
edit rights over the edge, or every route change went through the platform team.
Gateway API lets a platform team own the `Gateway` and hand app teams their own
`HTTPRoute` objects in their own namespaces, attaching to it only where allowed.

The features that were annotations become spec: weighted backends (canaries),
header matching, request mirroring, typed filters. `TCPRoute` and `GRPCRoute`
cover what Ingress never could.

Ingress is not going away — it's frozen, not deprecated, and it's fine for
"one host, a few paths". Reach for Gateway API when you need routing the spec
can't express, or when the ownership boundary above is a real problem for you.
